# Architecture

What VoltaCheck is made of, right now — not a plan. For the same thing drawn
rather than described — the module graph, the boot sequence, what a report and
a submission each go through — see [`docs/diagrams.md`](diagrams.md).

Both files describe the code as it is, so both go stale the moment it
changes. "Keeping the docs true" in `CLAUDE.md` lists which section and which
diagram each kind of change has to update, in the same commit as the change.

## No build step

`index.html` is a static page: markup, styles, and one
`<script type="module" src="app/main.js">`. The `app/` modules are native ES
modules — the browser loads and links them directly, nothing is compiled or
bundled. GitHub Pages serves the repo as-is from `main`.

`package.json`, `package-lock.json`, and `node_modules/` exist only for the
test suite described below. They are never served to a browser and never sit
between a commit and what Isabel sees live. If a change to `app/` or
`index.html` "just works" when opened as a file, it works in production —
there is no separate build artifact that could differ from the source.

## Module layout

| Module | Responsible for |
|---|---|
| `index.html` | Markup and CSS only. Boots the app via one module `<script>` tag. |
| `app/config.js` | `SUPABASE_URL` / `SUPABASE_ANON_KEY` and every tunable: `STALE_AFTER`, `RECONFIRM_AFTER`, `LOOKBACK_H`, `PAGE`, pin cap, the clustering threshold, cell size and minimum group (`CLUSTER_BELOW_ZOOM`, `CLUSTER_CELL_PX`, `CLUSTER_MIN`), colours (`COLOR`, plus `FADED`/`FADED_INK` for aged reports), labels, and the telemetry knobs (`RELEASE`, `TELEMETRY_FLUSH_MS`, `TRACE_SAMPLE`, `SLOW_SPAN_MS`). |
| `app/domain.js` | Pure status/search/decay logic, including `paintOf()` — how a decayed machine is drawn, as opposed to what it counts as. See below — this is the module that matters most. |
| `app/store.js` | In-memory `machines`/`selected`/`activeChain`/`activeStatuses`/`userPos` state, plus localStorage persistence (`localSeed`, `localLoad`, `localSave`, `deviceId`) for local mode. `activeStatuses`/`userPos` are deliberately never persisted. |
| `app/api.js` | Supabase reads and writes: `connect`, `pull`, `pushReport`, `submitMachine`, and `pageAll`, the PostgREST paging helper. No-ops (or local-only stand-ins) when running in local mode. |
| `app/map.js` | Leaflet init, pin rendering (from `paintOf()`, so an aged report fades rather than going grey), viewport culling (nearest-to-user when a fix is known, nearest-to-map-centre otherwise), and — below `CLUSTER_BELOW_ZOOM` — drawing `clusterize()`'s groups of `CLUSTER_MIN` or more as counted bubbles instead of pins. |
| `app/ui.js` | The bottom sheet (incl. the distance line and the last-report timestamp), town search box, chain filter chips, status filter chips (the tally row), the active-filter badge and empty-state reset, toast. |
| `app/telemetry.js` | Spans, counters, histograms and logs, in OpenTelemetry's data model but not its wire format or its SDK. Off unless the app is live, never throws into the app, and sends nothing anyone typed. See `docs/observability-plan.md`. |
| `app/main.js` | Wires the modules together, decides live vs. local mode, starts the app, and calls `telemetry.start()` once that decision is made. |
| `seed/machines.js` | The generated `SEED` array (2,444 rows), imported by `app/store.js`. Regenerated by `tools/import_osm.py` — never hand-edited. |
| `admin/*` | The private dashboard at `/admin/`: `auth.js` (password, then a TOTP challenge), `data.js` (the five read RPCs plus the reshaping the charts want), `charts.js` (inline SVG — bars, a line, horizontal bars, a waterfall; no chart library), `screens.js` (Now / Activity / Behaviour / Health), `main.js` (wiring). English, unlike the app. Reads `../app/config.js`, so blanking the Supabase values takes it offline with the app. |

Data flows one way through this list for a page load: `config` → `store`
(seeded from `seed/machines.js`) → `api` (if live) refreshes `store` from
Supabase → `map` and `ui` read `store` and call back into it on user action →
`main` ties the callbacks together.

## Why `domain.js` is pure

`app/domain.js` exports `statusOf`, `paintOf`, `needsReconfirm`, `ago`,
`norm`, `groupTowns`, `townsMatching`, `filterByChain`, `chainCounts`,
`latest`, `metresBetween`, `formatDistance`, `sortByDistance`,
`filterByStatus`, `statusCounts`, `filterByDistance`, `suggestTown`,
`knownTowns`, and `clusterize`. None of them touch `document`, `window`, `localStorage`,
`navigator`, or `fetch` — and none of them call `Date.now()`. Every function
that cares about time takes `now` as an explicit epoch-millisecond argument
instead.

`statusOf` and `paintOf` are the same threshold asked two different
questions, and keeping them apart is what let the decay stop being grey
without weakening it. `statusOf` answers *what does this machine count as* —
past `STALE_AFTER` it is `"stale"`, so the filters and the counts never file
a day-old report under "Cheias". `paintOf` answers *how is it drawn* — it
keeps the reported colour and returns `faded: true`, which `map.js` renders
as a hollow pin and `ui.js` as a hollow pill. A machine nobody has ever
reported is the one case with no colour to keep: both call it stale, and
that is the only thing grey means now.

This is deliberate, not incidental style: `domain.js` is the specification
that the iOS and Android clients will need to reimplement byte-for-byte. The
18h staleness decay and the 3h reconfirm prompt are the actual product — see
"Key mechanic" in `CLAUDE.md` — so if a Swift and a Kotlin port quietly
disagree with this one about when a report goes stale, the app lies to
someone depending on which app they opened. Taking `now` as a parameter is
what makes that behaviour testable, in any language, without mocking a
system clock: a test just picks the epoch-millisecond values that put a case
on either side of a threshold.

`test/vectors/*.json` is the shared, language-agnostic contract those ports
assert against — plain, strict JSON, not JS-only. `test/unit/domain.test.js`
is the first thing that loads and checks it; a future `XCTest` or JUnit
target should bundle the same files and iterate them the same way, rather
than transcribing cases by hand. Full detail — the file-by-file breakdown,
the composed sheet-prompt rule, and two known quirks worth a deliberate
look before three platforms independently decide whether to preserve them —
is in `docs/domain-contract.md`.

## Test strategy: four layers

| Layer | Command | What it covers | Needs |
|---|---|---|---|
| Unit | `npm run test:unit` | `domain.js` against `test/vectors/*.json` — decay, reconfirm, search ranking, chain filtering. Pure functions, no I/O. | Nothing. ~100ms. |
| Integration | `npm run test:integration` | `app/api.js`'s paging against a **real** Postgres + PostgREST pair the suite builds and tears down itself (`test/integration/docker-env.js`) — RLS, `public.report_machine()`'s rate limiting and proximity check, the row-cap regression `schema.sql`/`seed/machines.sql` exist to prevent, everything `public.ingest_telemetry()` has to refuse (`telemetry.test.js`), and every way past `public.is_admin()` that must not work, with real signed JWTs (`admin.test.js`). Run with `--test-concurrency=1`: all three files drive one set of fixed-name containers. | Docker. ~20s. |
| E2E | `npm run test:e2e` | Real Chromium via Playwright, driving the actual `index.html` — map rendering, the sheet, search, chain chips, and the decay's rendered colours (`decay.spec.js`, `pin-colours.spec.js`). Most specs run in local mode; `telemetry.spec.js` and `admin.spec.js` swap supabase-js for a fake in-memory client so the app goes live, and the panel has something to draw, without a byte reaching the real project. | Chromium (via `npx playwright install`). ~85s. |
| CI | `.github/workflows/ci.yml` | Runs the three above, fastest-first, on every push to `main`. | GitHub-hosted runner only — no secrets. |

**E2E deliberately runs in local mode and can never reach the production
database.** `test/e2e/fixtures.js` stubs out `supabase-js` before the page
loads, so every e2e test exercises the localStorage fallback path, not
Supabase. That's a intentional gap, not an oversight — it's exactly why the
integration layer exists: it is the only layer that runs `schema.sql` and
`report_machine()` against a real database and would have caught the
shipped bug where an unpaged `live` pull silently showed ~40% of the
country (see `docs/seed-data-plan.md`). Unit tests catch a wrong decay
formula; integration tests catch a wrong query against a real database;
e2e tests catch a wrong wire-up of the two in an actual browser. No one
layer subsumes the others.

`npm test` (unit + e2e only) predates the integration suite and is left as
is; CI does not use it — the workflow calls `test:unit`, `test:integration`,
and `test:e2e` as three explicit steps so integration isn't silently
skipped.

## If you are starting the iOS or Android client, read this first

1. `app/domain.js` — the logic to port. Nineteen functions, two constants.
2. `test/vectors/*.json` (and `docs/domain-contract.md`) — the contract your
   port's tests assert against. Load the files as test resources; don't
   hand-transcribe cases.
3. `schema.sql` — the tables and the `report_machine()` RPC your client will
   call over PostgREST. `docs/rate-limiting-plan.md` explains what it does
   and doesn't stop.

Everything else in `app/` (`map.js`, `ui.js`, `store.js`, `main.js`) is this
web client's own UI wiring and isn't part of the contract a native port
needs to match.
